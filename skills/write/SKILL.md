# 技术写作风格

## 写作信条

**用公式说话。** 最好的表达方式不是文字堆砌，而是一个简洁的公式。将复杂概念提炼为数学表达式是最标志性的写作手法。

**结构本身就是内容。** 不依赖情绪渲染或修辞技巧，通过清晰的分层、对比、列举来传递观点。文章的价值来自于读者合上文章后脑中留下的那套结构。

**先有痛点，后有方案。** 每一篇文章都是因一个问题而起。开篇必须让读者先感受到这个痛点的真实性和普遍性，然后再给出解法。

**保持视角一致性。** 如果要从一个问题切入，一路追问到本质，就不要在中途切换到「我告诉你一个好东西」的节奏。一条线走到底。

## 文章原型

文章通常可归为以下四种原型：

**概念解构型**：拆解一个模糊但重要的概念（如 Agent、Harness），用公式给出明确定义，分析其组成部分，澄清常见误区。核心是"这个概念究竟是什么"。

**模式对比型**：将两种或多种方案并列分析（如 ReAct Loop vs Ralph Loop、Workflow vs Agent、Edit vs Agent），用对比矩阵、优劣分析给出选型建议。核心是"什么时候该用哪个"。

**实践方法论型**：基于真实项目经验，总结出一套可复用的方法或架构。从问题出发，给出完整的设计思路和实现细节（含代码/配置/流程图）。核心是"我是怎么做的，你也能这样做"。

**深度思考型**：针对一个特定领域的工程挑战，层层深入分析。技术架构选择 → 核心设计 → 难点逐个击破。这类文章最长，信息密度最高。核心是"这个问题的完整解法是什么"。

## 风格特征

### 公式定义

最核心的风格标签。不是每个概念都要有公式，但关键概念必须用一个简洁的数学表达式来定义。

**模式**：提炼为变量 → 建立关系表达式 → 逐项解释每个变量的含义

**示例**：
```
Agent = LLM + Context + Loop
V(AI APP) ∝ V(M) × V(C) × V(P)
Harness = Agent + State + Reins
Agent Application = Application + Agent + MCP
State = GitHub | GitLab
```

公式不需要严格的数学意义，但必须有清晰的语义。每个变量在后续解释中逐一被展开。

### 结构化标题体系

文章结构必须清晰可见。使用分层标题体系，层级之间逻辑递进。

```
## 一级标题

### 二级标题

#### 三级标题
```

通常结构：
```
## 前言（问题引入）
## 核心概念 / 核心公式
## 分点展开（2-4 个主要板块）
## 总结
```

### 对比分析

核心是**同时抛出两个对象，在一个维度上对比**。不单独讲 A 再讲 B，而是反复横跳对比。

**常用对比维度和句式**：

```
| 维度 | A | B |
|------|---|---|
| 核心机制 | ... | ... |
| 适用场景 | ... | ... |
| 优势 | ... | ... |
| 局限 | ... | ... |
```

对比后往往跟着一个**混合策略**或**选型建议**——不做非此即彼的判断，给出折中或结合方案。

### 层次递进

从内到外、从底层到上层、从简单到复杂的递进结构是标志性写法。

**常见递进模式**：
- 内循环 → 外循环 → 双循环结合
- 内层 → 中间层 → 外层
- 基础版 → 进阶版 → 混合版

### 架构图驱动

当涉及流程、架构或交互时序时，可以用 Mermaid 图辅助说明。图放在文字解释之后，作为视觉总结。

**常用图类型**：
- `flowchart`：展示流程/循环
- `sequenceDiagram`：展示交互时序
- `stateDiagram`：展示状态流转
- `graph LR/TB`：展示架构层级

### 技术细节不回避

文章不是科普文。该贴代码就贴代码，该列配置就列配置。代码示例是论证的一部分，不是装饰。

代码块遵循以下原则：
- 用 TypeScript 表达逻辑框架，用伪代码表达核心思想
- XML/JSON 格式用于定义协议或数据结构
- 代码不追求完整可运行，追求「一看就懂核心逻辑」

### 总结矩阵

每篇文章结尾可以用一个总结性表格收束，三列：

| 概念/组件 | 职责 | 价值 |
|-----------|------|------|
| ... | ... | ... |

表格之后是一个简短的段落升华，一句话点出全文核心洞察。

## 写作流程

### 第一步：确定选题方向

先判断素材适合哪种文章原型：

- **概念解构型**：素材中有一个被过度使用但定义模糊的术语（Agent、Harness、MCP、Vibe Coding）。
- **模式对比型**：素材中有两个或多个可以放在一起比较的方案或工具。
- **实践方法论型**：素材中有真实项目经验和可复用的架构设计。
- **深度思考型**：素材针对的是一个特定领域的工程挑战，有足够多的维度可以深入分析。

### 第二步：搭建文章框架

```
【标题】直接、精确、不标题党
  ↓
【前言】痛点引入 → 点明核心观点 → 给出核心公式（如果有）
  ↓
【主体】2-4 个并列或递进板块
        每个板块内部：观点 → 分析 → 例证（代码/图/表）→ 小结
  ↓
【总结】总结表格 → 升华一句话
```

### 第三步：正文写作

**开头写法**：从问题出发，不绕弯子。

- **直接破题**："AI 技术快速发展，使得 AI 概念层出不穷……本文将结合自身学习，探讨 AI 应用的核心。"
- **痛点先导**："然而，这条路走起来并不轻松。让 Agent 持续迭代一个真实项目，意味着……"
- **核心定义先行**："Agent 的核心价值在于将复杂任务自动化分解和执行，而实现这一能力的关键就是 Loop 机制。"

**段落结构**：

每段应该承载且只承载一个信息点。段落之间严格递进，不跳跃。避免「另外」「顺便说一下」这种打断逻辑流的过渡。

**展开方式**：

```
观点句 → 解释句（可选）→ 例证（代码/图/表/对比矩阵）→ 小结句（可选）
```

**收尾写法**：

1. **总结表格**：一行一个核心组件，三列（组件、职责、价值）。
2. **升华句**：一句话点出全文核心洞察。句式：**"将需要 X 的 Y Z 化，是持续迭代的最佳实践。"** 或 **"X 的核心是 Y。"**
3. **引用结语**：引用权威资料中的一句话作为整篇文章的收束。引用后不需要再补充任何解释。

### 第四步：自检

**内容层**：
- [ ] 核心公式是否精确表达了文章的核心观点？
- [ ] 每个概念是否都有明确的定义？
- [ ] 对比分析是否在一个维度上进行？
- [ ] 技术细节是否准确且必要？
- [ ] 总结表格是否涵盖了文章的核心内容？

**结构层**：
- [ ] 标题层级是否正确递进？
- [ ] 段落之间是否有断裂或跳跃？
- [ ] 是否可以考虑添加图来表示复杂过程？

**表达层**：
- [ ] 没有冗余的修饰词和空话
- [ ] 没有不必要的感性表达
- [ ] 中英文术语混用是否自然（英文术语在中文文本中不加引号，保持自然）
- [ ] 代码块与正文的比例是否合理？

## 风格注意事项

### 可以用

- **数学符号**：∝、∀、∈、→、← 等，用在公式和关系表达中
- **Mermaid 图**：任何可以可视化的流程都应该配图
- **对比矩阵**：Markdown 表格形式的对比
- **箭头和流程表述**：用 → 表示流程走向，不需要写成"然后"
- **TypeScript 风格的伪代码**：用 async/await、while 循环等表达逻辑
- **XML 标签**：用于定义协议或数据结构
- **emoji 点缀**：适度使用，仅用于标记特殊条目 💡 ⚠️ 🔔

### 避免

- **情绪化修辞**：不写"太震撼了""太牛逼了"，保持理性语调
- **叙事性开头**：不写"故事是这样的"，直接进入问题
- **过度口语化**：不写"这玩意""坦率的讲"，保持简洁专业
- **第一人称主观判断**：不写"我觉得""我认为"，改为客观陈述
- **华丽的过渡句**：不写"值得注意的是""不难发现"，直接说
- **引用名人名言**：除非是技术文档中的原文引用
- **假设性例子**：不编造"比如有一次..."，使用真实项目经历或学术文献中的案例

## 文章长度

- 概念解构型：3000-5000 字
- 模式对比型：3000-6000 字
- 实践方法论型：4000-8000 字
- 深度思考型：6000-12000 字
- 每个代码块或图表控制在 20 行以内，太长就拆
- 段落平均 3-5 句话，每句不超过 40 个字

## 中英文混排规则

- 英文技术术语保持原文：Agent、Loop、RAG、LLM、MCP、Vibe Coding、Prompt Engineering、Context Engineering、Human-in-the-Loop 等
- 中英文之间加空格："Agent 的交互" 而非 "Agent的交互"
- 英文术语首次出现时，如果中文没有约定俗成的翻译，就保持英文
- 专有名词大小写保持原样：TypeScript、Mermaid、Claude Code、Langchain
